## 1. Непокриті вимоги (Uncovered REQ)

У матриці прапорцями $\text{🏳️}$ позначено такі вимоги: **REQ-003**, **REQ-004**, **REQ-016**, **REQ-017**. Жоден Use Case у таблиці не пов'язаний із ними (`x` відсутні).

* **REQ-003** (`WHILE` статус акаунту є `deactivated`, система `SHALL` забороняти дії, окрім активації/видалення):
* *Чому непокрита:* У переліку UC немає окремого варіанта використання на рівні бізнес-логіки системи для перевірки обмежень заблокованого/деактивованого акаунту під час спроби виконати заборонені дії (або це передбачено як загальний системний перехоплювач/middleware, який не винесено в окремий UC).


* **REQ-004** (`WHILE` статус акаунту є `banned`, система `SHALL` блокувати доступ):
* *Чому непокрита:* Аналогічно до REQ-003, блокування на рівні системи не має прив'язки до окремого сценарію використання (UC), хоча технічно воно покривається перевірками статусу (наприклад, `CheckAccountStatus`).


* **REQ-016** (`WHEN` користувач надсилає запит на деактивацію власного акаунту):
* *Чому непокрита:* У секції «Акаунт» є UC із назвою `DeactivateOwnAccount` (**UC25**), але в матриці зв'язків рядок `REQ-016` залишився порожнім. Вимогу слід зв'язати з UC25.


* **REQ-017** (`WHEN` деактивований/заблокований користувач надсилає запит на активацію/розблокування):
* *Чому непокрита:* У системі є відповідні UC для активації (`ActivateOwnAccount` — UC27, `ActivateAccount` — UC28), проте в самій матриці зв'язки для REQ-017 не проставлені.

## 2. Непокриті Use Cases (Uncovered UC)

На схемі прапорцями $\text{🏳️}$ позначено такі варіанти використання: **UC8**, **UC20**, **UC21**, **UC22**, **UC23**, **UC24**, **UC37**, **UC38**. Вони не мають позначок зв'язку (`..> : include` / `extend` або зв'язків з акторами) або не покриті жодною вимогою в таблиці.

* **UC8** (`Перевірити існування повідомлення`):
* *Пояснення:* Використовується через зв'язок `include` у сценарії `ReplyMessage`, проте в самій матриці реквізитів немає окремої вимоги (REQ), яка б формалізувала цю перевірку.


* **UC20** (`Перевірити статус спільноти`):
* *Пояснення:* Використовується як `include` для `SendMessageCommunity` та `DeleteCommunityMessage`, але не має прямого відображення у вигляді окрекреної вимоги (REQ) у таблиці.


* **UC21** (`Перевірити членство у спільноті`):
* *Пояснення:* Підключається через `include` до `SendMessageCommunity`, проте не прив'язаний до жодного REQ-параметра.


* **UC22** (`Перевірити власність спільноти`), **UC23** (`Перевірити статус модератора спільноти або вище`):
* *Пояснення:* Технічно використовуються як базові перевірки (мідлваре/гварди) для таких дій, як видалення чи редагування, але в таблиці вимог (REQ-001 — REQ-026) для них відсутні окремі деталізовані бізнес-вимоги.


* **UC24** (`Веріфікувати токен бота`):
* *Пояснення:* Використовується через `include` для `RetrieveNewMessages` (бот модерації), але не винесений у таблицю як окрема вимога REQ.


* **UC37** (`Перевірити статус адміна платформи`), **UC38** (`Перевірити статус модератора платформи або вище`):
* *Пояснення:* Слугують внутрішніми перевірками доступу (guard-функціями) для адміністративних і модераторських дій, проте в матриці вимог вони не задокументовані окремими рядками REQ.
