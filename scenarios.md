
### Сценарій 1. Спроба неактивного/забаненого користувача надіслати повідомлення

* **User Story:**
> *Як система безпеки платформи, я хочу автоматично блокувати спроби надсилання повідомлень від користувачів із деактивованим або забаненим статусом, щоб запобігти порушенню правил та несанкціонованій активності.*

* **Gherkin-сценарій:**
```gherkin
Scenario Outline: Блокування надсилання повідомлень для неактивних користувачів
  Given акаунт користувача має статус "<user_status>"
  When користувач намагається надіслати текстове повідомлення в чат
  Then система повинна заборонити операцію та повернути помилку доступу
  And запис у таблиці повідомлень не повинен створюватися

  Examples:
    | user_status  |
    | deactivated  |
    | banned       |

```

### Сценарій 2. Обмеження прав модератора спільноти щодо топ-ролей

* **User Story:**
> *Як система контролю привілеїв, я хочу забороняти модератору спільноти видаляти контент або виганяти учасників із ролями власника чи іншого модератора, щоб захистити ієрархію управління всередині спільноти.*

* **Gherkin-сценарій:**
```gherkin
Scenario Outline: Модератор спільноти намагається покарати користувача з вищим або рівним статусом
  Given користувач із роллю "moderator" у спільноті ініціює дію "<action>"
  When цільовим об'єктом є користувач із роллю "<target_role>"
  Then система повинна відхилити запит та заблокувати виконання дії

  Examples:
    | action             | target_role |
    | видалити повідомлення | owner       |
    | видалити повідомлення | moderator   |
    | вигнати з спільноти  | owner       |
    | вигнати з спільноти  | moderator   |

```

### Сценарій 3. Автоматичний захист привілейованих користувачів від дій Бота-модератора

* **User Story:**
> *Як внутрішній сервіс модерації, Бот має отримувати нові повідомлення через API, але не мати прав на видалення повідомлень, які належать власнику або модераторам спільноти.*

* **Gherkin-сценарій:**
```gherkin
Scenario: Бот модерації намагається видалити повідомлення модератора через API
  Given Бот модерації успішно отримав нові повідомлення спільноти через API (оновивши bot_last_message_received)
  When Бот надсилає запит на видалення повідомлення, автором якого є користувач із роллю "moderator"
  Then система повинна відхилити запит бота з помилкою доступу
  And повідомлення повинно залишитися в базі даних незмінним

```

### Сценарій 4. Управління створенням спільноти та неможливість виходу власника

* **User Story:**
> *Як користувач платформи, я хочу створити власну спільноту та стати її власником, при цьому система має гарантувати, що я не зможу випадково чи навмисно залишити її без передачі прав.*

* **Gherkin-сценарій:**
```gherkin
Scenario: Створення спільноти та спроба власника вийти з неї
  Given користувач створює нову спільноту через запит до платформи
  When система створює запис у сутності "community" та додає користувача в "membership" з роллю "owner"
  And власник надсилає запит на вихід (leave) із цієї спільноти
  Then система повинна заблокувати запит на вихід та повернути помилку логічної цілісності

```

### Сценарій 5. Перевірка коректності контексту чату під час створення відповіді

* **User Story:**
> *Як активний учасник чату, я хочу відповідати на конкретні повідомлення в межах одного чату, а система повинна гарантувати цілісність зв'язків і коректне збереження контенту.*

* **Gherkin-сценарій:**
```gherkin
Scenario: Користувач створює відповідь на повідомлення у межах того самого чату
  Given активний користувач перебуває у чаті спільноти з ID "10"
  When користувач надсилає відповідь (`replies_to_id`), що посилається на оригінальне повідомлення з того самого чату "10"
  Then система успішно перевіряє збіг ідентифікаторів чату
  And зберігає новий запис у сутності "community message" із прив'язкою до автора та часу створення

```
